# V48.3 全新需求识别与会话重置

## 🐛 问题描述

**用户场景**：
1. 用户先生成了一个"函数单调性"的教案
2. 然后输入："下周有个示范课观摩活动，主题是概率统计，需要规范的教案"
3. **系统错误行为**：认为是在修改上一个教案，回复"教案已经根据您的意见完成了全面修订。本次修改的核心是将课题从'函数的单调性'调整为'概率统计'..."

**根本原因**：
- 信息提取时使用了"增量提取"策略
- LLM看到已有信息（函数单调性），误以为用户是在修改
- 没有识别出这是**全新的教案需求**

---

## ✅ 修复方案

### 修复1：提示词增强 - 明确区分全新需求 vs 修改需求

**文件**: `backend/app/core/unified_lesson_plan/methods/extract_lesson_plan_info.py`

**新增内容**（第29-47行）：
```python
## 重要判断：是全新需求还是修改需求？

**首先判断用户意图：**
- **全新需求**：用户提出了一个全新的课题（如"概率统计"、"三角函数"等），与之前的课题完全不同
  - 特征：出现了新的课题名称、新的教学主题
  - 处理：**清空已有信息**，只提取最新输入中的信息
  
- **修改需求**：用户在之前生成的教案基础上提出修改意见（如"把第一课时改一下"、"增加一个例题"）
  - 特征：没有新的课题名称，只是对现有教案的调整
  - 处理：**保留已有信息**，增量提取修改内容

**判断示例：**
- "帮我生成一个概率统计的教案" → 全新需求（清空已有信息）
- "下周有个示范课，主题是概率统计" → 全新需求（清空已有信息）
- "把刚才的教案改一下" → 修改需求（保留已有信息）
- "增加一个例题" → 修改需求（保留已有信息）
```

**关键改进**：
- ✅ 明确告诉LLM如何区分两种需求
- ✅ 提供清晰的判断规则和示例
- ✅ 指导LLM在不同情况下的处理方式

### 修复2：代码逻辑 - 自动检测并重置会话

**新增逻辑**（第149-161行）：
```python
# V48.3修复：判断是否为全新需求
# 如果提取到了新的topic，且与已有信息的topic不同，说明是全新需求
if "topic" in extracted and extracted["topic"]:
    existing_topic = existing_info.get("topic", "")
    new_topic = extracted["topic"]
    
    if existing_topic and existing_topic != new_topic:
        print(f"🔄 V48.3检测到全新需求：'{existing_topic}' → '{new_topic}'，清空已有信息")
        # 清空已有信息，只保留新提取的信息
        session["collected_info"] = {}
        existing_info = {}
```

**工作原理**：
1. LLM提取到新的`topic`（如"概率统计"）
2. 检查已有信息中的`topic`（如"函数单调性"）
3. 如果两者不同 → **判定为全新需求**
4. **清空session中的collected_info**
5. 重新开始收集新教案的信息

## 💡 技术细节

### 判断逻辑

```python
if existing_topic and existing_topic != new_topic:
    # 全新需求
    session["collected_info"] = {}
else:
    # 修改需求或首次生成
    pass
```

**关键点**：
1. `existing_topic`存在 → 说明之前已经生成过教案
2. `existing_topic != new_topic` → 说明是新课题
3. 两个条件都满足 → **全新需求**

### 会话状态管理

**session结构**：
```python
session = {
    "collected_info": {
        "topic": "函数单调性",
        "student_level": "高一",
        "usage_scenario": "daily_teaching",
        ...
    },
    "lesson_plan": "...",
    "conversation_history": [...]
}
```

**清空操作**：
```python
session["collected_info"] = {}
```

这样下次提取信息时，`existing_info`就是空的，LLM会当作全新需求处理。

## 🎯 边界情况处理

### 情况1：用户没有明确说课题

**用户输入**：
```
帮我生成一个教案，高二学生
```

**处理**：
- LLM可能无法提取到明确的`topic`
-  fallback机制：使用整个用户输入作为topic
- 不会触发清空逻辑（因为没有明确的topic变化）

### 情况2：用户说了相似但不完全相同的课题

**用户输入**：
```
用户1：帮我生成一个函数的教案
用户2：帮我生成一个函数单调性的教案
```

**处理**：
- `existing_topic` = "函数"
- `new_topic` = "函数单调性"
- 两者不同 → 触发清空
- ✅ 这是合理的，因为"函数单调性"是更具体的课题

### 情况3：用户想修改但换了说法

**用户输入**：
```
用户1：帮我生成一个函数单调性的教案
用户2：我想讲一下单调性的应用
```

**处理**：
- `existing_topic` = "函数单调性"
- `new_topic` = "单调性的应用"
- 两者不同 → 触发清空 ❌

**潜在问题**：这可能是一个修改需求，但被误判为全新需求。

**解决方案**（未来优化）：
- 增加语义相似度判断
- 如果新旧topic高度相关（如都包含"单调性"），则视为修改需求
- 可以使用向量相似度或关键词重叠度来判断
